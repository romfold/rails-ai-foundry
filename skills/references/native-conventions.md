# Native context conventions

Explicit `foundry check --sources` and `foundry adopt --sources` inspect shell app/ and
all upstream package app/ Ruby files, including packages without foundry.yml. Discovery
does not assign a profile or namespace: domain rules require the owning context's
explicit intent. Review files_checked and diagnostics separately from behavioral evidence;
zero configured contexts does not mean zero source coverage. Lib/test and non-Ruby files
remain outside this check. Keep Packwerk and HTTP/browser verification separate.

For a new application, `foundry new NAME` delegates to Rails and defaults to Spec Kit. Explicit `--specs=openspec|none` is supported. Foundry belongs to development/test; application execution uses packs-rails, Dry::Operation and Rails directly. The default stack is PostgreSQL, Puma, Hotwire and Solid Queue, without an additional cache service. Inspect interrupted creation before retrying; the command never merges into an existing destination.

Read the owning `package.yml` and adjacent `foundry.yml`. Profiles are `rails_native`, `modular`, and `domain`. Event and CQRS patterns are independent. Capability selections never silently promote a profile. Use the consuming application's existing package roots; new contexts default to `packs/`.

Use direct upstream packs commands for package operations; read [pack operations](packs.md). Optional `foundry:context NAME --profile=PROFILE` and component generators with `--context=NAME` offer small scaffolds. Native command, query, model, operation, entity, value-object, policy, port, and repository placement follows the selected profile. Migrations remain in the Rails application root. Introduce repositories and ports for an actual boundary; efficient Active Record reads remain valid in every profile.

Domain commands under `app/application/billing/commands/` define `Billing::Commands::*`. Modular commands under `app/commands/billing/` define `Billing::*`. Models inherit the host's `ApplicationRecord`. Native operations inherit `Dry::Operation`, use `skip_prepending`, and establish one `steps`/`step` result boundary. Transactional commands inspect the failed result inside the transaction and raise `ActiveRecord::Rollback`. The generated savepoint prevents nested failed writes from leaking. Application callers decide whether a failed inner command also aborts their larger transaction.

Feature-owned delivery stays in the pack; Rails base classes and shared delivery stay in the shell. Same-pack delivery can call internal application objects. Cross-pack callers use declared dependencies and public contracts. Upstream `packs-rails` provides Rails loading. Foundry has no application loader.

For AI, select `capabilities.ai.adapter: ruby_llm` explicitly and add optional RubyLLM `~> 1.16.0` to the application bundle. Optional `foundry:agent NAME --context=NAME` creates direct RubyLLM agents/tools/schemas and plain `app/prompts` instructions inside the owning pack, a behavioral contract and an evaluation starting case. Fill the application-owned `config/ai.yml` model aliases and pass a selected alias's model/provider options to the agent constructor, together with `operation:` and `authorize:` callables. Authorization must bind a trusted principal and run before each tool execution; the operation enforces tenant scope. Generated instructions use `File.read(File.expand_path(..., __dir__))`, avoiding ERB evaluation of injected Proc inputs and working-directory assumptions. Keep user/tool content in its message role, validate structured output in application code, and add offline workflow tests. Explicit `foundry check --prompts` verifies declarations and files; it does not execute evaluations or establish model quality.

Replace scaffold exceptions with meaningful behavior and tests. Keep normal tests offline and external requests outside database transactions. Use constructor injection. Do not introduce a Foundry container, event bus, aggregate engine, projection runtime, AI execution store, or specification-provider abstraction.

Use `foundry plan refactor --context=NAME --profile=PROFILE` for a read-only assessment. Its detected references are source evidence, not proof of runtime reachability, a data conversion, or a completed migration.

Read root `config/foundry.yml` before generation: its defaults apply to new contexts unless explicitly overridden. `foundry:context` accepts independent `--events` and `--cqrs` selections; selecting a pattern records intent and does not install a capability implementation. Workload never changes another axis automatically.

Start native adoption with `foundry adopt --format=json`. It preserves established workflow selection, existing roots, specifications and accepted Packwerk debt. `foundry check` validates configuration and namespace ownership without Rails boot. Explicit `foundry check --boundaries` runs upstream Packwerk validate/check in the locked consumer bundle and test environment; use an isolated test application because initializers may execute. It preserves accepted debt files, propagates upstream failures and never regenerates baselines. Review fully resolved baselines separately: Packwerk 3.1.0 can miss those stale entries. Run behavioral tests separately, and do not claim pks parity or complete debt cleanup from this check.

Optional ROM writes must persist business state and outbox intent through the same ROM gateway transaction, with explicit rollback of failed native results. Deliver to RES or another destination after commit with stable IDs and idempotent recovery. dry-system is optional wiring and Trailblazer an alternative native workflow; neither warrants a Foundry container or result wrapper.

For Foundry 1.x tooling upgrades, inspect `foundry --version` and `foundry contracts` before interpreting configuration or JSON evidence. Reports identify report_schema, foundry_version and report_kind; reject unsupported schemas and ignore additive fields. Read success/complete and the declared limitations, not completion prose. Root schema 1 rejects unknown fields; checks/adoption currently have no policy keys. Use explicit CLI checks instead of inventing configuration switches.

A gem update does not rewrite application code or installed skills. Preserve receipts and local edits. Compare fresh output in a disposable destination, then apply reviewed changes with behavioral tests. For a complete current eight-skill catalog, `bin/rails generate foundry:skills --upgrade` provides read-only assessment; explicit digest-bound apply preserves conflicts pending recorded review. Read the installed gem’s docs/skill-upgrades.md before applying or recovering. Historical catalogs still require manual review; never edit receipt hashes to bypass a conflict. Preserve workflow history and accepted debt, and regenerate old parity evidence against the current inputs. The installed gem's docs/stable-contracts.md describes compatibility and recovery policy.

For AI artifacts, `foundry check --prompts` covers every upstream package prompt root, including packages without foundry.yml. Use the actual deepest package as contract owner; apply namespace intent only from that owner’s explicit configuration. Missing contracts and unsafe artifacts fail; zero contracts is not AI acceptance. Review newly exposed findings explicitly, preserve prompt/agent receipts, and run authorization, provider-failure and evaluation tests separately with offline inputs.
